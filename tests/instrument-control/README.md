# Instrument control integration tests

The measurement Lua scripts use native `InstrumentTarget` accessors and
`instrument_call_stack.new(...)` with direct `ctx:call(...)` calls. They do not
require the source/multimeter wrapper modules. The recent hub-config and ISA
updates retain the `SET_VOLTAGE`, `GET_VOLTAGE`, and `GET_DATAPOINT` commands, so
the direct-call changes remain compatible at the command interface.

## Scripts and test boundaries

- `measurement-scripts/`: `measure_get_set.lua`, `measure_1D_buffered.lua`, and
  `measure_2D_buffered.lua`. The sweeps perform scalar reads at each point;
  they do not implement hardware-buffered acquisition.
- `settings-scripts/`: plain Lua voltage, sample-rate, and sample-count get/set
  scripts using direct ISS calls. See their [argument and command reference](settings-scripts/README.md).
  Separate settings request/response integration tests are still pending.
- `lua-utils/`: sweep interpolation using native `InstrumentDomain` accessors.
  Import `sweep_math`; `require("math")` resolves to Lua's built-in module.
- `instrument-libs/`: legacy wrappers. The measurement scripts, new settings
  scripts do not load them.
- `.tl` files are legacy sources and are not kept in sync with the direct-call
  Lua changes. The current Lua test path does not compile Teal.

`measure_get_set` currently accepts `ctx, setVoltages, getters, setters`, with
voltages in a positional array in setter order. This matches the current hub
encoder. Differences from `falcon-measurement-lib` schemas, including voltage
maps, acquisition arguments, and declared return units, remain to be reconciled.

| Test path | What it exercises | Hub config |
| --- | --- | --- |
| `DataRetrievalTest.measure_set_get` | `MeasurementRequest` → NATS → hub → ISS → Lua → plugins → `MeasurementResponse` | Existing `WriteConfigFile()` fixture |
| `DataRetrievalTest.*` | Controller → NATS → hub → ISS → mock plugins | Generated by `WriteConfigFile()` |
| Separate settings pipeline | `SettingRequest` → hub settings router → `SettingResponse` | Planned; not yet implemented |

The scalar test lives in `data-retrieval.cpp` and reuses its existing hub/ISS
fixture and single-point request builder. It does not test the settings pipeline.
See the [pipeline checklist](../../docs/MEASUREMENT_AND_SETTINGS_TEST_PLAN.md)
for the remaining split between measurement and settings integration tests.

## Generated hub configuration

`DataRetrievalTest` writes `tests/test-runs/<test-run>/test-config.yaml` at
runtime. Edit [WriteConfigFile()](data-retrieval.cpp) to change its contents;
editing a previous run's YAML will not affect the next test.

For `measure_set_get` only, the fixture stages `measure_get_set.lua` into a
private `scripts/` directory and copies `get_voltage.lua` / `set_voltage.lua`
under the hub registry's `get_source_voltage.lua` / `set_source_voltage.lua`
names. The generated config points there. No sweep primitives are enabled,
so the scalar test avoids sample-count/averaging prerequisites. Other tests
retain their existing script directory. The readiness helper retries the initial
NATS connection while the hub starts ISS, then waits for hub status.

The config now contains the inline wiremap, device config, database paths and
owner, working directory, script directory, and ISS startup settings. Instrument
types and characteristic identifiers must match the schema shipped with the
selected vcpkg hub release; a sibling hub checkout may have a different schema.

| Instrument | Config type | Characteristic mappings |
| --- | --- | --- |
| Source1 | `dc_voltage_source` | `source_voltage`: `GET_VOLTAGE` / `SET_VOLTAGE` |
| Meter1 | `voltmeter` | `sample_rate`: currently write-only `SET_SAMPLE_RATE`; `number_of_samples`: `GET_BINS` / `SET_BINS` |

The fixture currently configures embedded NATS at `127.0.0.1:4222`, sets
`NATS_URL=nats://localhost:4222`, and uses ISS RPC port `5555`. If the NATS host
or port changes, update `NATS_URL` in the same fixture. Prefer deriving both
from the same values when updating the setup.

The recent pull corrected YAML command spacing and the empty `readCommand`
mapping. The following remaining issues concern the older tests and future
settings/sweep coverage:

- Other tests still point `user-measurement-luas` to `tests/lua`, while the maintained
  measurement scripts live here. Stage the intended Lua scripts into the
  fixture's configured directory, preferably per run. Make `sweep_math`
  available to ISS when enabling the sweep scripts.
- Stage the new `settings-scripts/*.lua` files as well. The hub registry expects
  `get_source_voltage.lua` / `set_source_voltage.lua`, so copy or rename the
  `get_voltage.lua` / `set_voltage.lua` files when preparing that directory.
  Sweeps need `get_number_of_samples.lua` plus an initialized positive sample
  count. Providing the scripts does not repair the config or meter getters.
- The new mock meter getters return `g_num_bins[channel]` and
  `g_sample_rate[channel]` despite computing a zero-based `index`. Use `index`
  for readback. Also reconcile `GET_SAMPLE_RATE`'s ISA input list: it currently
  declares a `sample_rate` input while the plugin getter expects only a channel.

Validate the generated hub YAML separately from the instrument ISAs. Passing
the ISA validators does not establish that the hub config or complete pipeline
is ready. Older hub tests also retain assertions and readiness behavior that
need review during the pipeline migration.

## Run the scalar measurement test

After your manual build, run from the controller repository:

```sh
. build/linux-clang-release/env.sh
export PATH="$VCPKG_INSTALLED_DIR/$VCPKG_TRIPLET/bin:$PATH"
export LD_LIBRARY_PATH="$VCPKG_INSTALLED_DIR/$VCPKG_TRIPLET/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
ctest --preset linux-clang-release \
  -R '^DataRetrievalTest\.measure_set_get$' --output-on-failure -V
```

The test sets S1 (Source1 analog channel 1) to 0.123 V and reads O1
(Meter1 analog channel 1) through `measure_get_set.lua`. It checks the response's
connection, instrument type, volts, and single sample against the first value
in `tests/test-data/gaussian-1d.txt`, generated by the existing fixture. The mock
meter is independent of the source, so its reading need not equal 0.123 V.

The test is part of `integration_tests`. There is no separate
`measure-set-get.cpp` test executable or `test-utils.cpp` dependency. Logs,
generated hub config, and staged scripts remain under
`tests/test-runs/DataRetrievalTest_measure_set_get_*` for inspection.
No passing build or runtime result is implied by this source update.
